# Gaia synthetic photometry handoff

## Goal

Make Gaia DR3 synthetic photometry the primary reference for **every workflow that currently uses APASS anywhere in VaST**. Try a complete local Gaia Synthetic Photometry Catalogue (GSPC) installation first, then query the ESA Gaia Archive. If Gaia cannot supply enough usable matches in the requested band, try APASS DR9 via ESA TAP, APASS DR9 via VizieR, and finally Pan-STARRS1 via VizieR. The two supported Gaia deployments are a live ESA query and a full all-sky local copy. Keep the existing explicit Tycho-2 and astrometry-only modes.

Status on 2026-11-23: the APASS query via ESA TAP is the only part that exists in the code. The Gaia lookup, the local copy and the Gaia-first selection are not started. The plan was reviewed on that date against the ESA bulk download, the ARI copy of the Gaia Archive and the VizieR mirrors. The ESA Archive and CDS VizieR were both down during the whole review, so nothing below has been run against the live ESA service unless the text says so.

## What is implemented

- [The APASS client](../lib/apass_esa_tap.sh) submits a bounded TAP request to `https://gea.esac.esa.int/tap-server/tap/sync`. It uploads the reference coordinates as a VOTable, searches `external.apassdr9` by `raj2000` and `dej2000`, and returns the brightest usable V-band match per target. The returned target ID maps directly back to the original solver star.
- [The solver](../src/solve_plate_with_UCAC5.c) tries the ESA client in `search_APASS()` before the existing VizieR APASS query. Invalid replies, transport failures, and fewer than four usable matches fall through to VizieR. The ESA result is applied only after the entire normalized response passes validation. Both APASS paths share the same missing-error defaults and Cousins R/I transformations through `set_apass_photometry()`.
- The runtime Gaia GSPC lookup, full-copy installer, and Gaia-first selection are the next implementation work.

Known gaps in the APASS step (review of 2026-11-23):

- The query has still not run against the live archive. As committed it ordered by table-qualified names (`ORDER BY t.target_id, a.vmag, a.recno`), which the ARI Gaia TAP service rejects with HTTP 400 (`Encountered "."`); had ESA done the same, every call would have failed and the solver would have continued silently with VizieR. Since 2026-11-23 it orders by `target_id, vmag, recno`. The request of the corrected client, sent to ARI with a small uploaded table in place of `external.apassdr9`, returned the expected rows in 0.6 s: the brightest match first, `recno` deciding between equal V, sources outside the cone or the magnitude range left out, a missing g as an empty field. Still to confirm on ESA: the column names of `external.apassdr9`, the run time of the join for 1000 positions, and the reply format.
- The repository has no test of the client or of `read_APASS_from_esa_tap()`. The harness described at the end of this document was not committed. A `curl` stub placed first in `PATH` drives the client and the solver offline; [the astrometry safety test](../util/examples/test_astrometry_safety.sh) uses the same technique.
- The two APASS paths do not select identical stars. The ESA query takes the brightest match that has B, V, r and i, and accepts a missing g (written as 0.000 with the default error 0.020). The VizieR path takes the brightest V match and then drops the star when any of the ten values is blank. A valid ESA reply with too few matches is still followed by the VizieR APASS query, which can only repeat it.
- The client does not use `VAST_CURL_PROXY`. It has no memory of a failed request, so a hanging archive costs up to 90 s for every image; [the VizieR mirror probe](../lib/choose_vizier_mirror.sh) keeps a short-lived shared record for the same reason.

## Gaia catalogue

The ESA table is `gaiadr3.synthetic_photometry_gspc`: 218,936,915 sources, all with G < 17.65 and BP/RP spectra. It holds `source_id`, `c_star` and, for every band, `<band>_mag`, `<band>_flux`, `<band>_flux_error` and `<band>_flag`. It has no coordinates. Join `gaiadr3.gaia_source` on `source_id` for the position (epoch 2016.0), proper motion and `phot_variable_flag`. Johnson B and V are `b_jkc` and `v_jkc`, Cousins R and I are `r_jkc` and `i_jkc`, Sloan g, r and i are `g_sdss`, `r_sdss` and `i_sdss`. A live ESA join for a 0.25-degree cone centered at RA 291.769208 and Dec +15.467964 returned 20 validated I-band sample rows for Gaia G between 9 and 14; the same cone on ARI holds 167 such sources. [ESA data model](https://gea.esac.esa.int/archive/documentation/GDR3/Gaia_archive/chap_datamodel/sec_dm_performance_verification/ssec_dm_synthetic_photometry_gspc.html) | [GSPC paper](https://arxiv.org/abs/2206.06215)

- **Each band is null independently.** A magnitude is listed only when flux / flux_error > 30 in that band. In 2070 rows of the bulk download B is missing for 12 percent of the sources, g for 4 percent, V for 0.9 percent, r for 0.2 percent, and R, I and i for none.
- **Uncertainty.** Use `(2.5 / ln(10)) * flux_error / flux`, with positive flux. It never exceeds 0.036 mag and is about 0.001 mag for bright stars. Apply a floor, as [the Seestar script](../util/seestar_photometry.sh) does with 0.01 mag, or a handful of bright stars carries every weighted fit.
- **The flag is a validity range, not a quality mark.** It is 1 when G and BP-RP of the source lie where the standardisation was validated. Measured on 8709 sources with G < 14.5 in a 2-degree cone at RA 100, Dec +30: the V, R and I flags are 0 for every source brighter than G = 10.80 and 1 for 99.9 percent of the fainter ones (the exceptions are redder than BP-RP = 2.6); the B flag needs in addition 0.50 <= BP-RP <= 1.70, which leaves 93 percent of the fainter ones; the g, r and i flags are 0 for every source brighter than G = 14.20 and 1 for all fainter ones. Requiring flag = 1 would remove every comparison star brighter than G = 10.8, the range where Gaia is expected to replace saturated APASS photometry, and nearly every Sloan-band comparison star of a small telescope.
- **Blends.** `c_star` is the corrected BP/RP flux excess. Its absolute value has a median of 0.008 and exceeds 0.09 for 10 percent of the sampled sources; large values mark blended or otherwise disturbed photometry.
- **Depth.** Nothing is fainter than G = 17.65. Deep narrow fields whose unsaturated stars are all fainter keep depending on Pan-STARRS1.
- **Photometric systems.** GSPC g, r, i are standardised to the SDSS system, APASS lists g', r', i'. Cousins R and I come directly from Gaia instead of the Jester et al. (2005) transformation of APASS V, r' and i'. Expect zero-point and colour-term shifts against earlier APASS-based results and measure them.

## Online sources

**ESA Gaia Archive** (`https://gea.esac.esa.int/tap-server/tap/sync`). The intended query uploads the reference positions as the APASS client does, joins `gaiadr3.gaia_source` by a cone around each position and `gaiadr3.synthetic_photometry_gspc` by `source_id`. This upload join has not been timed on ESA: measure it for 20, 200 and 1000 positions before building on it. Service behavior measured on 2026-11-09 (see `.claude/notes.md`): a request that follows another within seconds, and any burst, is refused with HTTP 429; synchronous replies arrive at about 1500 rows per second and are cut at 50000 rows unless `MAXREC` asks for more; anonymous asynchronous jobs are aborted after 60 s. During maintenance the service answers HTTP 200 with an HTML page, so validate the reply itself. The ADQL rules below were established on ARI and still need confirming on ESA: an `ORDER BY` with table-qualified names is rejected, and so is one with a name that two joined tables share (`source_id`); column positions and names unique in the join are accepted. NULL arrives as an empty CSV field.

**ARI** (`https://gaia.ari.uni-heidelberg.de/tap/sync`) serves the Gaia DR3 tables under the same table and column names and stayed up while ESA was down. A cone on `gaia_source` joined to the GSPC works there: 167 rows for the 0.25-degree cone above in 11 s, 8709 rows for the 2-degree cone of the flag measurement in 25 s. A cone the size of the TESS frame (radius 8.5 degrees, G < 10.5) did not finish in 170 s. A join of an uploaded table with `gaia_source` does not: it timed out after 120 s for two positions. ARI has no `external.apassdr9`.

**VizieR** serves the GSPC as `I/360/syntphot`, with the coordinates in the same table: `Source`, `RA_ICRS`, `DE_ICRS` (epoch 2016.0, no proper motions), `E(BP/RP)corr` (the `c_star` value) and, per band, flux, flux error, magnitude and flag, for example `FV`, `e_FV`, `Vmag`, `VFlag`. The band letters are B, V, R, I, g, r, i. The Seestar script queries this table already, and the list query and the parser of the APASS VizieR path fit it with little change. On 2026-11-23, with CDS down, vizier.cfa.harvard.edu, vizier.idia.ac.za and vizier.nao.ac.jp answered single cones of this table, CfA with database errors in between. None answered a list query usefully: CfA returned a complete but empty table at once, IDIA needed about 2 s per position and dropped a list of 150, NAO returned nothing in 68 s. A field cone with a magnitude range worked on CfA and IDIA: 410 rows for a 2-degree radius and V from 4 to 11, in 54 s and 92 s.

On 2026-11-23 ESA and CDS were down together. The photometric lookup for one TESS frame took about 7 minutes to fail: 1 s for ESA, then four APASS and four Pan-STARRS1 attempts through VizieR. With the provider order of the goal, every image taken during an ESA outage is calibrated against APASS, or against nothing.

## Local copy

ESA lists 44 gzipped CSV files totaling 41,976,759,812 bytes, about 42.0 GB or 39.1 GiB, and `_MD5SUM.txt` with their checksums. The files are ECSV: several hundred header lines starting with `#` (389 in the first file), a line of column names, then data with the word `null` for a missing value. They hold `source_id`, `c_star` and the photometry, and no coordinates. The rows are not in sky order: 2070 consecutive rows of the first file fall into 1981 different HEALPix level-8 pixels spread over the whole sky. [ESA bulk listing](https://cdn.gea.esac.esa.int/?prefix=Gaia/gdr3/Performance_verification/synthetic_photometry_gspc/) | [Catalogue statistics](https://gaia.aip.de/metadata/gaiadr3/synthetic_photometry_gspc/)

Coordinates and proper motions come from the `gaia_source` bulk files: 3386 gzipped CSV files, 753,025,661,884 bytes or 753.0 GB, each named after the range of HEALPix level-8 pixels it holds (`GaiaSource_000000-003111.csv.gz`). The level-8 pixel of a source is `source_id >> 43`, so the GSPC rows can first be sorted into the same 3386 ranges and then joined to one `gaia_source` file at a time as it streams through. [The Gaia DR2 installer](../lib/install_local_copy_of_GaiaDR2.sh) streams 588 GB that way: 2 h 8 min on tau with 12 parallel downloads, checksum tests and resume after interruption. The DR3 CSV quotes strings and writes `null`, unlike DR2.

Store the result in the zone format of [the local catalogue tool](../src/catalogs/local_star_catalog.c) with a wider record: identifier, position, proper motion, G, the seven magnitudes with their errors and flags, `c_star` and the variability flag. That is about 50 bytes per source, 11 GB in all. Give the tool a list mode, so that one process answers all positions of an image. Record the release in `catalog_info.txt`, which is written last so an incomplete build is never used. Build the catalogue once and publish the finished files on the mirrors, as for [the nearby Gaia DR3 copy](../lib/install_local_copy_of_GaiaDR3_nearby_stars.sh): other hosts then download 11 GB instead of streaming 795 GB.

## Decisions to make before coding

- **Validity flags.** Proposed rule: prefer flag = 1, accept flag = 0 where the magnitude range of the image offers too few flagged stars, and log the number of each. Before relying on unflagged bright stars, compare them with Tycho-2 V and with APASS on NMW and TESS fields; the Seestar notes report agreement of the V zero points within 0.04 mag.
- **Bands are filled independently.** `set_apass_photometry()` blanks a star unless B, V, r and i are all present, and both APASS queries require the same. Applied to Gaia, that rule would discard every star without B, 12 percent of the catalogue, whatever band was asked for. The solver does not know the requested band, and its catalogue is cached and reused for other bands. Proposed rule: write every band Gaia has for each star, count usable stars per band, and fill from the fallback providers only the bands that fall short, so each band column comes from one provider. The alternative is to pass the requested band to the solver. Check first that no consumer combines two band columns of one row.
- **Matching and crowding.** The APASS queries take the brightest source within the search radius, which is 35.4 arcsec for the TESS frame, and the reference positions are UCAC5 positions at the UCAC mean epoch of each star (1998 to 2004). For Gaia, propagate the reference positions to 2016.0 with the UCAC5 proper motions and take the nearest source within one or two arcseconds. Then decide how to treat neighbours inside the measuring aperture of cameras with large pixels: add their fluxes (the flux columns and one zero point per band make that exact), or reject crowded comparison stars as the Seestar script does. Gaia resolves pairs that APASS measured as one star, so this changes zero points in crowded fields.
- **One provider per run.** ESA refuses bursts, so parallel plate solving would hand Gaia to some images and APASS to others of the same light curve, with a zero-point step between them. A provider change inside a run has to be visible and preventable: honor 429 with a spaced retry before falling back, remember a failed service for a few minutes in a shared record, and offer a setting that pins the provider. Production hosts should use the local copy.
- **Second online Gaia source.** Decide whether `I/360/syntphot` is tried after ESA and before APASS. It keeps the photometric system unchanged while ESA is down, at the cost of one more client; its list query needs CDS itself.
- **Cuts and weights.** Start with the 0.01 mag error floor, a limit on the absolute `c_star` value (0.1, or the magnitude-dependent limit of Riello et al. 2021) and exclusion of sources with `phot_variable_flag = VARIABLE`, then tune them on a crowded Milky Way field.
